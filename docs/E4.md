# Conseils personnalisés par IA : synthèse du prototype

## 1. En résumé

- **Le projet est faisable.** Un prototype fonctionne : à partir des séances d'un utilisateur, l'API Gemini génère un bilan et 3 conseils au format JSON, directement affichables dans le tableau de bord.
- **Durée estimée de l'intégration : 3 à 4 semaines** pour un développeur (détail en partie 9).
- **Conditions avant la mise en production** : passer par un backend, utiliser le palier payant de l'API, recueillir le consentement des utilisateurs (RGPD) et mettre en place un suivi de la qualité des réponses.

## 2. Démarche

| Étape                       | Travail réalisé                                                                                                   |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 1. Découverte de l'API      | Tests dans Postman : modèles disponibles, paramètres (température, réflexion, longueur), conversation, erreurs    |
| 2. Définition de la requête | Requête finale avec authentification, modèle de body, vérification automatique des réponses, exemples enregistrés |
| 3. Conception des prompts   | Prompt structuré en sections, données utilisateur préparées par le backend, comparaison de 3 formulations         |
| 4. Synthèse                 | Le présent document                                                                                               |

## 3. Choix techniques

| Choix                                                                     | Raison                                                                                                                        |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| API Gemini au lieu de Mistral                                             | Contrainte du projet. Fonctionnement équivalent, avec une sortie JSON contrôlée par un schéma                                 |
| Modèle Flash, nom configurable                                            | Bon rapport qualité, vitesse et coût. Le nom n'est pas codé en dur, car un modèle a été retiré pendant les tests (erreur 404) |
| Appels via le backend uniquement                                          | La clé API ne doit jamais être visible dans le navigateur                                                                     |
| Sortie JSON avec schéma                                                   | Réponse directement exploitable : 3 cartes de conseils avec une priorité                                                      |
| Température 0                                                             | À température 1, le modèle a inventé des faits absents des données. La valeur 0 a donné les réponses les plus fidèles         |
| Réflexion limitée (`thinkingLevel: low`), sortie plafonnée à 2 048 tokens | La réflexion interne a représenté jusqu'à 66 % des tokens d'un appel. Le plafond borne le coût                                |
| Données pré-calculées par le backend                                      | Le modèle ne calcule rien (allures, totaux, distance max), ce qui supprime les erreurs de calcul                              |
| Données minimisées                                                        | Ni nom, ni photo, ni poids. L'âge est transmis en tranche                                                                     |
| Avertissement médical ajouté par l'application                            | Texte fixe et validé, toujours présent, au lieu d'être laissé au modèle                                                       |

## 4. Raisonnement derrière les prompts

**Séparer les instructions et les données.** Le prompt système est identique pour tous. Les données de l'utilisateur sont envoyées à part, en JSON. On peut ainsi faire évoluer l'un sans toucher à l'autre.

**Structurer en sections.** Contexte, tâche, ton, description des données, règles, format, exemple. Chaque section répond à une question que le modèle se poserait sinon.

**Une règle pour chaque défaut observé.** Les règles ne sont pas théoriques, elles viennent des tests :

| Défaut constaté en test               | Règle ajoutée                                                     |
| ------------------------------------- | ----------------------------------------------------------------- |
| Alternance tutoiement / vouvoiement   | Tutoiement imposé                                                 |
| Markdown dans le texte                | « Pas de markdown »                                               |
| « Belle progression » sans historique | Interdiction d'affirmer une évolution sans données de comparaison |
| Passage proposé de 12 à 14 km (+17 %) | Distance maximale fournie et à respecter                          |
| Titre contraire au contenu            | Cohérence titre / détail exigée                                   |

**Montrer plutôt que décrire.** Un exemple de réponse dans le prompt fixe le niveau de détail et le style attendus.

**Préparer les données compte autant que le prompt.** Avec les mêmes données pré-calculées, un prompt d'une phrase respecte déjà la distance maximale. Le prompt structuré apporte surtout la fidélité aux données et la constance du ton.

## 5. Métriques proposées

| Domaine      | Métrique                                                                             | Mesure                                                                         |
| ------------ | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| Conformité   | Taux de réponses au JSON valide et complet                                           | Automatique, à chaque appel                                                    |
| Conformité   | Taux de respect des règles : 3 conseils, tutoiement, distance ≤ max                  | Automatique, à chaque appel                                                    |
| Fidélité     | Taux de réponses citant un chiffre absent des données                                | Automatique : comparaison des chiffres de la réponse avec les données envoyées |
| Qualité      | Note de pertinence, clarté et utilité (1 à 5)                                        | Relecture mensuelle d'un échantillon de 50 réponses, idéalement par un coach   |
| Satisfaction | Taux de « utile / pas utile » par conseil                                                          | Boutons dans l'interface                                                       |
| Usage        | Part des utilisateurs qui demandent des conseils, et à quelle fréquence              | Analytics                                                                      |
| Technique    | Temps de réponse, taux d'erreur (429, 503), taux de réponses servies depuis le cache | Logs du backend                                                                |
| Coût         | Tokens et coût moyen par génération, coût mensuel total                              | `usageMetadata`, enregistré à chaque appel                                     |

## 6. Limites et risques

**Limites de l'approche actuelle**

- **Peu de tests** : un seul profil d'utilisateur et un seul cas limite, avec un seul essai par réglage. Les conclusions (température, choix du prompt) restent à confirmer sur un plus grand échantillon.
- **Réponses non déterministes** : la même requête ne donne jamais exactement la même réponse.
- **Inventions possibles** : réduites par le prompt, mais pas supprimées.
- **Cas limites fragiles** : avec une seule séance, le modèle a proposé deux sorties de 1,7 km, vouvoyé l'utilisateur et fait une faute de langue.
- **Conseils parfois vagues** : « ralentis légèrement » n'est pas une consigne précise.
- **Coût variable** : de 545 à 1 496 tokens par appel selon le prompt et la réflexion du modèle. Le prompt retenu est 3,5 fois plus long que la version simple.
- **Données limitées** : Sportsee ne connaît ni l'objectif de course de l'utilisateur, ni ses sensations. Les conseils restent donc généraux.
- **Prototype non intégré** : les tests ont été faits dans Postman. Le comportement réel dans l'application reste à valider.

**Risques**

| Risque                                        | Conséquence                         | Réponse prévue                                                              |
| --------------------------------------------- | ----------------------------------- | --------------------------------------------------------------------------- |
| Modèle retiré ou remplacé par Google          | Panne ou changement de comportement | Modèle configurable, modèle de secours, tests rejoués à chaque changement   |
| Surcharge de l'API (503 fréquents en gratuit) | Conseils indisponibles              | Réessais, derniers conseils en cache, palier payant                         |
| Conseil inadapté ou risqué                    | Blessure, perte de confiance        | Règles du prompt, limite de distance, contrôles automatiques, avertissement |
| Dérive des coûts                              | Budget dépassé                      | Quotas par utilisateur, cache, alertes de budget                            |
| Fuite de la clé API                           | Utilisation frauduleuse et facturée | Clé côté serveur uniquement, rotation régulière                             |

## 7. Questions éthiques

- **Santé** : les conseils ne sont pas un avis médical. Le modèle ne pose pas de diagnostic (vérifié en test avec une douleur au genou), et l'application affiche toujours un avertissement.
- **Données personnelles** : la fréquence cardiaque peut être considérée comme une donnée de santé. Il faut un consentement explicite, une information claire sur l'envoi à un service tiers (Google), et la possibilité de désactiver la fonctionnalité. En gratuit, Google peut réutiliser les données : la production doit passer par le palier payant.
- **Transparence** : les conseils doivent être présentés comme générés par une IA.
- **Publics fragiles** : les conseils ne sont pas adaptés aux personnes blessées, enceintes ou en reprise après une maladie. Il ne faut jamais générer de conseils liés au poids, à cause du risque pour les personnes souffrant de troubles alimentaires.
- **Confiance excessive** : un utilisateur peut suivre un conseil sans recul. Le ton doit rester suggestif (« essaie de… ») et jamais injonctif.
- **Impact environnemental** : chaque génération consomme de l'énergie. Le cache et la génération à la demande limitent les appels inutiles.

## 8. Impacts sur l'expérience utilisateur

| Sujet                                | Recommandation                                                                                                 |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| Temps de réponse (quelques secondes) | Génération au clic sur un bouton, avec un indicateur de chargement, plutôt qu'à l'ouverture du tableau de bord |
| Erreurs de l'API                     | Afficher les derniers conseils disponibles ou un message simple, jamais un écran d'erreur                      |
| Lisibilité                           | Une carte par conseil, une couleur par priorité, et la `donneeCle` reliée au graphique correspondant           |
| Confiance                            | Mention « Conseils générés par IA », boutons « utile / pas utile », date de génération                                       |
| Ton                                  | Bienveillant et non culpabilisant, y compris quand l'objectif n'est pas atteint                                |
| Quota                                | Indiquer à l'utilisateur combien de générations il lui reste dans la journée                                   |

## 9. Recommandations pour l'implémentation

**Estimation**

| Tâche                                                                               | Durée                                      |
| ----------------------------------------------------------------------------------- | ------------------------------------------ |
| Endpoint backend : préparation des données, appel à l'API, validation de la réponse | 3 à 4 jours                                |
| Gestion des erreurs, cache, quotas, suivi des coûts                                 | 2 jours                                    |
| Interface : cartes de conseils, chargement, erreurs, retours « utile / pas utile »                | 2 à 3 jours                                |
| Jeu de tests de prompts (une dizaine de profils types) et ajustements               | 3 jours                                    |
| Consentement et mentions RGPD                                                       | 1 à 2 jours, plus une validation juridique |
| Bêta auprès d'un petit groupe d'utilisateurs et corrections                         | 1 semaine                                  |
| **Total**                                                                           | **3 à 4 semaines**                         |

**Ordre de mise en œuvre conseillé**

1. Backend et validation automatique des réponses
2. Jeu de tests de prompts, à rejouer à chaque modification du prompt ou du modèle
3. Interface et consentement
4. Bêta limitée, avec suivi des métriques de la partie 5
5. Ouverture à tous si les métriques sont satisfaisantes

## 10. Pistes d'amélioration

**Prompt (version suivante)**

- Exiger une action précise par conseil : quoi, quand, combien.
- Interdire explicitement le vouvoiement et toute mention d'un organe ou d'un effet sur la santé.
- Raccourcir l'exemple pour réduire le coût.

**Données**

- Appliquer un plancher à la distance maximale conseillée (par exemple 10 km), pour éviter les conseils absurdes sur un faible volume.
- Ajouter à Sportsee un objectif déclaré par l'utilisateur (« courir un 10 km », « reprendre le sport »), pour des conseils vraiment personnalisés.

**Technique**

- Mettre le prompt système en cache côté Gemini (`createCachedContent`), puisqu'il est identique pour tous les utilisateurs.
- Afficher la réponse au fur et à mesure (streaming), pour réduire l'attente perçue.
- Comparer d'autres modèles : Flash-Lite, moins cher, ou Mistral, hébergé en Europe.
- Évaluer automatiquement les réponses avec un second modèle chargé de les noter selon une grille (_LLM-as-a-judge_).
- Comparer deux versions de prompt auprès de deux groupes d'utilisateurs (A/B test), en s'appuyant sur les retours « utile / pas utile ».

**Fonctionnalités**

- Un plan d'entraînement pour la semaine (jours, distances, allures).
- Une conversation avec le coach. Cette fonctionnalité est plus coûteuse, car tout l'historique doit être renvoyé à chaque message, et elle présente plus de risques, car l'utilisateur écrit librement.
